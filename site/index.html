fn median(xs: [f64]) -> f64?:
    """The middle value of `xs` once sorted; None when `xs` is empty."""
    if len(xs) == 0:
        return None
    var s = xs
    s.sort()
    mid = len(s) // 2
    if len(s) % 2 == 1:
        return s[mid]
    return (s[mid - 1] + s[mid]) / 2.0

fn spread(xs: [f64]) -> f64:
    m = median(xs) ?? 0.0
    return m - xs[0]

test "median of three":
    assert median([3.0, 1.0, 2.0]) == 2.0

test "median of four":
    assert median([4.0, 1.0, 3.0, 2.0]) == 2.5

The loop

One program, two readers

The model writes it, the compiler answers in a form the model can act on, and a person reads what is left — with nothing hidden from either.

01 The model writes

  • Python's vocabulary, so its prior helps
  • One canonical form, enforced by lotml fmt
  • todo() fills a hole and still compiles
  • Edits addressed by symbol, not by line
→

02 The compiler answers

  • Types checked on prefixes, mid-write
  • Diagnostics as versioned JSON with a fix hint
  • explain, digest, show for context
  • The same tools over LSP and MCP
→

03 The person reviews

  • Every failure path in the signature
  • No aliasing: an assignment copies
  • Every match covers every case
  • test blocks live beside the code

What's inside

A small language with checked guarantees

Static types, value semantics and errors as values, in a syntax a Python reader already knows.

Python where it means Python

Same keywords, same indentation, same for and match — so a model's training prior helps instead of misleading it.

Errors as values

No exceptions. T ! E is a result, fail returns the error, ? passes it up. Every failure path is in the signature.

Value semantics

An assignment copies, with reference counting and reuse underneath. Nothing changes behind a caller's back.

Types checked on prefixes

Static types the checker can judge while the code is still being written — feedback before the function is finished.

A compiler built as a tool

check, explain, digest, show, an LSP server and an MCP server, all answering in versioned JSON.

test blocks in the language

Tests sit beside the code they cover, and a failed comparison reports both values it saw.

A tour

Familiar where it can be, explicit where it must be

Each difference from Python is one a reviewer can see on the page.

users.lot
type User(name: str, age: int, email: str? = None)

fn find_email(users: [User], name: str) -> str?:
    for u in users:
        if u.name == name:
            return u.email
    return None

fn contact(users: [User], name: str) -> str:
    email = find_email(users, name)
    if email is not None:
        return email
    return "no email"

T? is the only type that admits None

x is not None narrows x to T inside the block, and x ?? default unwraps with a fallback.

Not Python: no truthiness. if and while take only bool.

parse.lot
type ParseErr = Empty | NotNumber(text: str) | Negative(value: int)

fn parse(s: str) -> int ! ParseErr:
    if s == "":
        fail Empty
    n = s.to_int() ?? fail NotNumber(s)
    if n < 0:
        fail Negative(n)
    return n

fn double(s: str) -> int ! ParseErr:
    n = parse(s)?
    return n * 2

A failure is a value of the return type

T ! E is a T or an error of type E. fail e returns the error; expr? unwraps or passes it up.

Not Python: no raise, try or except. The program stops only on a broken invariant.

point.lot
type Point(x: f64, y: f64)

fn nudged(p: Point) -> Point:
    var q = p
    q.x = q.x + 1.0
    return q

test "the original is untouched":
    p = Point(1.0, 2.0)
    q = nudged(p)
    assert p.x == 1.0
    assert q.x == 2.0

Records are values

q = p copies. A field changes only through a var, and a plain parameter is read-only.

Not Python: no aliasing surprises — reference counting and reuse keep the copy cheap.

shape.lot
type Shape = Circle(r: f64) | Rect(w: f64, h: f64) | Empty

fn area(s: Shape) -> f64:
    match s:
        case Circle(r):
            return 3.14159 * r * r
        case Rect(w, h):
            return w * h
        case Empty:
            return 0.0

Sum types and exhaustive match

Variants are constructors in scope; patterns bind fields by position or name.

Not Python: match must cover every case — a missing variant is a compile error.

append.lot
fn add_all(inout xs: [int], values: [int]):
    for v in values:
        xs.append(v)

test "inout changes the caller's var":
    var xs = [1]
    add_all(&xs, [2, 3])
    assert xs == [1, 2, 3]

Mutation is spelled at the call

To change a caller's value, the parameter says inout and the call passes &x, where x is a var.

Not Python: a function gets a copy through a plain parameter; sink takes the value over.

The harness guide

A small model that points, and knows when to stay quiet

When check refuses the code or a test fails, a half-billion-parameter coder model tuned on LotML tells any coding agent where to change it and what kind of change it needs. It runs on your own CPU. The agent still does the editing.

  1. The agent asks

    guide is one more tool of the compiler's MCP server, so any harness and any model can call it — or run lotml guide ask from a shell.

  2. The compiler finds the state

    The first file with errors and its diagnostics, or the first failing test block with the values each side of its comparison had.

  3. The model points

    One to three ranked locations — a path, a symbol and a line span — and a kind of change, held to a JSON schema at temperature zero.

  4. The compiler checks the answer

    A location must name a real file and a declared symbol. Below a calibrated confidence the guide says nothing rather than guess.

  5. An edit is shown only once it holds

    Applied to a copy: the tests unchanged, the file checking clean, the failing test passing. Your files are never written.

How it compiles

One IR. Two targets.

One lowering turns the checked program into one IR, which every backend reads, and every target is held to the same parity suite.

source parser checker
IR lotml-ir

Python target

Python backend → CPython

lotml run · lotml test

Reaches every Python library through checked boundaries and interface files.

LLVM target

monomorphize → counts → LLVM → native

lotml build · --shared

A native executable with no Python at run time, or a library C calls through its header.

Get started

Up and running in a minute

Releases hold lotml for Linux x86_64, Windows x86_64 and macOS on Apple silicon, beside the VS Code extension. run and test need Python 3.11+; a native build needs clang 17+.

lotml init                  # AGENTS.md, the guide, the MCP server
lotml check stats.lot       # syntax, type and mutability errors
lotml test  stats.lot       # run the test blocks
lotml run   main.lot        # run fn main()
lotml build stats.lot       # a native executable, through LLVM
lotml explain E0207         # explain an error code
git clone https://github.com/protonspy/lotml
cd lotml
cargo build --manifest-path compiler/Cargo.toml --locked --release -p lotml
